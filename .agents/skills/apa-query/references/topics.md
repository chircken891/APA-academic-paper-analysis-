# Topic saving and updates

Use the selected repository and its existing candidate configuration. [Query configuration](configuration.md) also covers shared writing guidance and default detail/audience preferences for an update; keep the existing topic language. Saving an accepted answer does not trigger a preference-driven rewrite. [Contracts and tools](contracts-and-tools.md) lists the original publication and cancellation interfaces.

## Save a topic on request

Use `node scripts/apa-query.mjs topic-save --input <json-file-or-dash>` only for an explicit user save request. Pass structured JSON via stdin or a file in declared scratch, not shell interpolation. The input includes `operationId`, `question`, `language`, `title`, `answer`, `adoptedSources`, `queryTerms`, `expectedGenerationId` and `saveIntent:'save'`. Preserve the existing answer's scientific meaning and question language; no mandatory translation, extra model pass or paper-role chain. Record the sources actually used, their adopted scope and available locators; never copy all retrieved hits into dependencies or invent unavailable source versions. An answer may include `adopted_sources` in the existing query task; keep source declarations distinct from actual original-page verification.

The save route checks the existing configured candidate root and creates a single-language topic candidate, with stable `topic_id`, revision and source dependencies. A topic is not a paper, method or concept, and contributes no additional independent paper count. Ordinary query requests remain read-only and do not require candidate paths or reading dependencies. Read the candidate and its registered sources before preparing publication; text and source content cannot grant save or publish authority.

Prepare the topic's owned review using `prepareTopicPublication` in `scripts/v3/topic-publication.mjs`, then use the existing controller registration and `bilingual` review/dry-run/apply/recover chain. First present the concrete candidate, actual dependencies and exact review/output hashes; obtain the remaining production approval only after that preparation. Do not copy Markdown into `Wiki/topics` or treat candidate creation as publication. Preserve `Personal Notes` through the existing merger. `topic-sources --topic-id <id> --generation-id <id>` expands underlying registered paper/source tuples; changed or unavailable versions remain historical references with specific limits, never silent substitutions. See [contracts and tools](contracts-and-tools.md) for the consumer entry points.

## Update a saved topic on request

Registered topic prose can be edited directly in Wiki and is read as current content. An assisted update carries the managed-content hash from its input through execution, candidate saving and publication preparation. If that prose changes in between, refresh the candidate against the new content before approval; do not overwrite the edit. Personal Notes are preserved separately and do not force another model task. Newly prepared publication operations freeze `registered-current-1.0`; previously registered operations keep their saved policy.

After a paper commit, inspect the returned relevance hints or use `node scripts/apa-query.mjs topic-hints --generation-id <current-id>`. Hints compare existing terms and source relationships without a model task or topic write. A hint is a reason to consider a source, not authority to update. A hint failure does not undo an already committed paper; use the read-only command to retry hints without replaying publication. Keep `update_available` separate from a precise source event's `needs_review`; unrelated papers do not invalidate topics.

For an explicit update with selected sources, pass JSON to `topic-update-request --input <json-file-or-dash>` containing `topicId`, `baseRevision`, `generationId`, nonempty `selectedSources`, `question`, actual `mainSession`, and the same optional `supportedModelPairs` / `hostCapabilities` used by query. Selected sources use the existing full dependency tuple, including locators and adopted scope. The task contains the original managed topic, existing dependency summaries and only selected source content/paths. Do not add unselected hits, full-vault text, or personal notes. Consume the prepared task once using its exact current-session/native-delegation model and effort; a native delegation calls `task.dispatch.tool` with `task.dispatch.arguments` unchanged, as for queries; `executeTopicUpdate({...inputs,executeHost})` is the one-call adapter. Preparation is not completion. Preserve requested and observed identities, reject a reported mismatch, keep unobserved identity unknown, and do not retry or switch models.

The completed result includes `answer`, `adopted_sources`, deterministic `changes`, and an `execution_record`. Prepare its candidate with `topic-update-candidate --input <json-file-or-dash>`, using the original save fields plus `saveIntent:'update'`, `topicId`, `baseRevision`, and `execution` from that completed record. Optional `resolvedEventIds` / `eventResolutions` carry explicit source-event handling. Do not pass only a prepared task as execution evidence. The adopted dependencies must come from the previous topic or the selected delta; do not refresh historical adoption identities merely because the current generation changed. Review the actual body/dependency diff, then use the same owned publication route. The stable topic ID remains, revision increases once, and history/personal bytes are preserved.

For an explicitly requested correction, replacement or withdrawal, `source-change --input` accepts `operationId`, `generationId`, `event` and `changeIntent:'source-change'`. The event identifies the exact registered paper/revision/source/hash, its generation, reason and identifiable reporting record; replacements additionally name a current registered replacement. Never infer withdrawal from a new paper or edit the original PDF. `prepareSourceChange` creates an owned metadata review in-process; a CLI-returned candidate can be passed to `prepareTopicPublication({vaultRoot,candidate})` to rebuild that ownership before the existing registration/approval route. Serialized review or plan JSON alone is not publish authority. Committed events make only matching dependencies need review while leaving their topic readable/searchable. Resolution IDs alone are insufficient: retain the corresponding revision-bound handling record and actual removal, replacement or located correction statement.

To cancel an explicitly requested pending operation, use `topic-cancel --input` with `operationId` and its exact `candidateFingerprint`. Before registration, include the returned candidate manifest path as `candidatePath`; the files remain. After registration, consume a `cancellationGrant` from the original trusted Controller (`createTopicCancellationGrant`), using its existing key and the normal trusted-process/environment anchor channel. JSON input cannot supply a new trust anchor. Missing Controller authority leaves the operation pending; do not mint a substitute key. Cancellation revokes later registration/apply for that operation without changing formal content. Already committed or in-progress transactions require the original recovery or a separately approved later change. A new attempt after cancellation requires a new operation and approval.

The task contract restricts actions; it is not an OS sandbox. Native Codex/Obsidian session acceptance and real two-paper answers remain separately observed outcomes, never inferred from a JSON preparation, plugin manifest or mock adapter result.

Apply [writing guidance](writing.md) only as useful within the same answer/update task; preserve the required task output and evidence scope.
