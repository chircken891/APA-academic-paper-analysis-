# APA project rules

- Before cloning, extracting, installing or writing configuration, require the user to choose or explicitly confirm the absolute project folder. Never default to the current chat folder or a child such as `outputs/APA`. Recommend setting the chosen project folder as the agent's working directory. Use that root explicitly in commands that accept a root argument; a different working directory does not change the target. Do not re-ask for the same already confirmed target. Keep task scratch files below that repository's `.tmp/<task>/`.
- Read root `README.md`, `SETUP.md`, and `docs/CONFIGURATION.md` before first use. Use the repository `apa-setup` skill to inspect or change personal configuration.
- Use `academic-paper-analysis` for paper reading and continuation. Use the repository `apa-query` skill for committed-library questions, source lookup, topic saving and selected updates; load its specific procedures only for that work.
- Personal configuration belongs only in ignored `config/apa.local.json`. A public export deliberately contains no personal answers. Missing required settings block a new configured reading; existing bound runs keep their frozen configuration.
- Installation permission is not permission to choose configuration. The user must select settings personally on the setup page or through grouped choices in the conversation: host dispatch, models and reasoning effort, output folders, parser location, writing order and presentation, then writing guidance. Ask query preferences separately, allowing an explicit decision to leave them unconfigured. Present concrete options and effects and wait for each group's answers. Requests such as "configure it for me", "you decide" or "use all recommendations" do not replace these choices.
- Detection results, historical defaults, recommendations and the only available option are not user answers. Preserve unanswered settings as missing or unchanged; never fill them to reach `ready`. Explain incompatible settings and ask the user to choose a supported value or defer; never silently switch to `follow-main`.
- Build operations only from the user's selections. Show the target folder and before/after differences, obtain explicit application confirmation, then use the existing CLI and read back the result. A complete user-supplied operation with an explicit apply request needs no repeated questions about the already selected target and fields. Never write personal configuration or operate the page to fabricate user choice or approval. Host detection reports are not saved configuration choices.
- Before any installation, produce a read-only report of available and missing prerequisites, exact selected targets and expected effects. Install only after the user explicitly authorizes that selection.
- Preserve source files, human notes, evidence and unrelated changes. Reading candidates do not authorize publication. Dependency installation, external writes, publication and Git operations require explicit user authorization.
- Use the V3 reading-first workflow and its source/evidence boundaries. Deliver coherent bilingual Obsidian notes. Keep scientific limits and unresolved issues visible; synthetic tests do not establish real-paper acceptance.
- Put reusable modules in `scripts/`, tests in `test/`, documentation in `docs/`, sources in `Raw/`, final authorized notes in `Wiki/`, and assets in `Figures/`. Method nodes belong in `Wiki/methods/`.
- Run the smallest relevant tests. Report changed files, validation and remaining limitations. Do not install dependencies or make global changes as a side effect of configuration.
- Report project acquisition, dependency installation, user-selected configuration saved, and readiness separately. Readiness does not establish successful model calls, PDF parsing or paper acceptance.
